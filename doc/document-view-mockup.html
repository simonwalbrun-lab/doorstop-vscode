1
A virtual fileScheme doorstop-doc:, served by a FileSystemProvider. Dirty state, undo, find/replace, multi-cursor all come from the editor for free.
2
Item markerOne HTML comment per item: UID, level, links, review state. Dimmed by a decoration and read-only — it's the key that maps the block back to SYS-0001.md.
3
Heading itemsNon-normative items with a header: render as headings; the depth follows the level (1.0 → #, 1.1 → ##). The level number is an inline decoration, not text.
4
Header and text are the editable partsThe ## line writes back to header:, the paragraphs to text:. Nothing else in the item file is touched.
5
Problems, in placeDoorstop's validation is mapped onto the marker line, so the same squiggles and quick fixes as in the item file appear here — Do Review also sits in the CodeLens.
6
Links stay navigableHover, F12 and the call hierarchy work on the UIDs in the marker, because the providers are registered for markdown, not for the file: scheme only.
7
New items always get a markerA heading typed without a marker is text of the item above — headings are legal inside item text, so they can't mark a boundary. + New item below (CodeLens) or Doorstop: Insert Item Here inserts a <!-- new item --> placeholder plus an empty heading; on save each placeholder becomes an item created after the block above it. Deleting a block asks before the file is removed.
8
Block stripingEvery second item is tinted with a faint whole-line background decoration (themeable colour doorstop.documentView.altBlockBackground), so block boundaries are visible without reading the marker lines. The tint follows the text as it is edited.

What happens on save

1 · SplitThe text is cut at the marker lines. Each block is {uid, header, text}; a block whose marker is <!-- new item --> is a new item; text is never split at headings.
2 · Diff per UIDHeader and text are compared with the item on disk. Unchanged items are skipped, so a save touches only what you edited.
3 · WriteChanged items get header:/text: updated in their file; new items go through the server; missing blocks prompt before deletion.
4 · RefreshDoorstop re-validates, the Problems panel and tree update, and the view is regenerated so review hashes and levels are current.

Editing rules

Part of the viewEditableWhere it goes
Heading line (## …)editheader: of the item
Paragraphs below the headingedittext: of the item, markdown kept as written
<!-- new item --> block (inserted by + New item below)editNew item created after the previous block on save
Heading typed without a markereditOrdinary text of the item above — never a new item
Marker line (UID, level, links, reviewed)read-onlyEdits are reverted; use the CodeLens or context commands (Link, Review, Clear) — same as today
Level number decorationread-onlyReorder via the tree / Reorder Document; the view regenerates
Order of blocksread-only (v1)Moving blocks could map to reorder later; v1 keeps it explicit to avoid accidental renumbering
