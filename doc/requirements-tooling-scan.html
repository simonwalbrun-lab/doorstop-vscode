Field scan · requirements tooling

How other requirements tools show and protect a document

A look across IBM DOORS Next, Jama Connect, Polarion, Codebeamer/Helix ALM, Modern Requirements, ReqView and StrictDoc — the viewing, traceability and review features they've converged on — read against Doorstop's item-file model and the 019 Document View spec, to find what's genuinely missing.

01

Tools scanned

From heavyweight, database-backed ALM suites to lightweight, plain-text, git-native tools — Doorstop's own end of the market.

IBM DOORS Next enterprise
Relational · Jazz platform

The traceability incumbent. Module-based documents, a graphical impact explorer and baselines are core, not add-ons — at the cost of a famously heavy, unintuitive editor.

Jama Connect enterprise
Cloud · review-centered

Best known for "Live Traceability" — replacing the static matrix with a continuously current upstream/downstream view, so gaps surface during development, not at audit time.

Polarion enterprise
LiveDoc editor

A "LiveDoc" is a merged, editable document over structured work items — the closest enterprise cousin to the 019 Document View — with named baselines and a side-by-side compare view built in.

Codebeamer & Helix ALM enterprise
Full ALM suites

Requirements as one module inside a bigger lifecycle tool — strong matrix and compliance tooling, customizable workflow, but the document is one view among many.

Modern Requirements Word / Azure DevOps
Smart Docs + trace analysis

Lives inside Word and Azure DevOps. Builds an end-to-end trace matrix "in under a minute" with Grid, List and Heatmap views, plus immutable milestone snapshots.

ReqView lightweight
Git/SVN-native

A single desktop app over a document tree, versioned in git. Tabular document editor plus generated multi-level traceability reports to Word/Excel/PDF.

StrictDoc closest analog
Plain-text · .sdoc + Git

Requirements as text files under version control, like Doorstop. Ships a web document editor, a spreadsheet-style bulk view, generated traceability matrices, and a tree-diff/changelog between two revisions.

Doorstop this project
YAML/MD items · Git

One file per item, links resolved by UID, review state tracked per item. The 019 spec adds a merged, editable document view on top of that model.

The 019 spec closes exactly one gap — the merged document view — and closes it well: it's the one row where Doorstop moves from "No" to sitting alongside Polarion's LiveDoc, StrictDoc and Modern Requirements' Smart Docs. Three columns stay empty even after 019 ships: coverage/gap analysis, a real baseline & diff view, and a traceability matrix beyond one item's call hierarchy. Doorstop already has the raw material for all three — it's the only tool here with both a merged document view and git-native storage.

03

Gaps & feature ideas for Doorstop

Each pattern below is standard in at least one tool above. The "for Doorstop" line is a concrete way it could work given the server-backed item index the 019 spec already relies on.

1

A traceability matrix / heatmap view

Seen in: DOORS Next, Jama Live Trace, Modern Requirements Heatmap, StrictDoc

Every mature tool eventually gives you a grid — upstream document down the rows, downstream document across the columns — colour-coded by link status, so gaps and orphans are visible at a glance instead of item-by-item.

For Doorstop: a webview panel, generated from the same server-backed index that already powers call hierarchy and suspect-link detection — cell states: linked, suspect, missing upstream, orphaned downstream. Clicking a cell opens that item's document-view block.
2

A baseline compare / diff view

Seen in: Polarion Document Baselines, StrictDoc tree-diff & changelog, Modern Requirements snapshots

Polarion's LiveDoc compare view and StrictDoc's changelog both render "what changed between two points" as readable prose — added/removed/changed items with header and text diffs — not a raw text diff of YAML.

For Doorstop: Doorstop already has this data for free in git history. A "Compare Document..." command could render the same document-view markup for two refs (branch, tag, commit) side by side, diffing at the block level — reusing the 019 spec's block model instead of a new one.
3

A coverage / orphan report

Seen in: DOORS Auto RTM, Jama Live Traceability, StrictDoc coverage views

Jama's pitch for Live Traceability is explicit: surface missing links "during development rather than during an audit." A standing report of items with no downstream link, or no upstream parent, does that without waiting for a review cycle.

For Doorstop: a Problems-panel-style list, or a dedicated explorer node, populated from validation the server already computes — this is largely a new view over existing suspect-link and missing-link diagnostics, not new analysis.
4

Multi-hop impact analysis, not just one hop

Seen in: DOORS graphical explorer, Jama Live Trace Explorer

Call hierarchy shows one item's direct links. Impact analysis in the bigger tools walks several hops upstream and downstream at once, so a change to a system requirement shows every test case it could eventually affect, not just its immediate children.

For Doorstop: extend call hierarchy recursively into a small graph view for "what does changing this item touch, transitively" — most valuable right before editing a widely-linked item, which the document view makes easy to do without noticing.
5

Review as an audit trail, not a flag

Seen in: Jama review center, DOORS/Polarion sign-off, redlining tools' change trails

Regulated tools don't just track "reviewed: true" — they keep who reviewed what, when, and against which content, because a boolean can't answer "did anyone actually re-review after this text changed."

For Doorstop: a lightweight history alongside the existing reviewed/suspect state — reviewer, timestamp, and the item's hash at review time — surfaced as a hover on the marker line the 019 spec already renders, no new storage format required beyond an optional field.
6

Export to a shareable static document

Seen in: ReqView (Word/Excel/PDF/HTML), StrictDoc, Modern Requirements' Smart Report

Every lightweight tool in this scan ends up generating a polished, standalone artefact for people who won't open the editor at all — a stakeholder, an auditor, a customer.

For Doorstop: the document view's rendering already produces exactly the content this needs — an "Export as PDF/HTML" command is largely a rendering target, not a new data model, and gives non-technical readers a document without a VS Code install.
7

A bulk, spreadsheet-style view alongside the document view

Seen in: StrictDoc's table view, DOORS' native grid, ReqView's tabular editor

StrictDoc deliberately ships two editors over the same data: a document view for reading and prose editing, and a spreadsheet view for comparing or bulk-editing attributes across many items at once — a different task, not a redundant one.

For Doorstop: a complementary "table view" for attributes the document view intentionally excludes (level, links, review state — FR-043) would give bulk operations a home without pulling scope into the document view itself.
8

A project-wide view across documents

Seen in: DOORS/Jama project hierarchies, Codebeamer trackers

Enterprise tools default to a project-level view spanning every document; single-document views are the drill-down, not the destination.

For Doorstop: explicitly out of scope for 019 (FR-045, "exactly one document") and reasonably so — but worth flagging as the natural next document-view-shaped feature once single-document reading and editing are proven out.
04

Patterns worth carrying forward

Less "add this feature," more "work this way" — the philosophy behind the tools above, independent of any one product.

Traceability should be live, not a periodic export

Jama's whole pitch is that a matrix generated once and pasted into a report is stale the moment anything changes. Doorstop's suspect-link mechanism already has this property — it just isn't presented as a standing view yet.

The document is the human interface; the matrix is the audit interface

Every serious tool keeps both, deliberately separate. The 019 spec earns the first half well. Treat the second half as a separate, later view rather than folding matrix concerns into the document.

Baselines should be named, not just commits

Polarion's baselines are git-like revisions with a human label attached. Doorstop already has git; a thin "name this state" layer over tags would make comparisons ("what changed since the v2 baseline") legible to non-technical readers.

Plain text and git are a genuine edge, not a limitation

ReqView and StrictDoc compete on this explicitly against DOORS-class tools. Doorstop's 019 spec leans into it — disk is the source of truth, diffs stay reviewable, nothing needs a database — worth defending as new views are added, not traded away for feature parity.
