# Feature Specification: Extension Settings

**Feature Branch**: `020-extension-settings`

**Created**: 2026-10-03

**Status**: Draft

**Input**: User description: "I want to have settings to configure the behaviour of the extension. The extension shall have following settings.
- checkbox to locate or not the currenlty open file in the vs code explorer
- checkbox for each problem report which can be generated by doorstop. If it shall be generated or not.
- settings for generating new documents via treeview buttons. markdown/yml  separator number of digits
- option for entering the template name to use during publishing documents"

## Clarifications

### Session 2026-10-03

- Q: When the "locate open file in the VS Code explorer" checkbox is off, which files should stop being revealed? → A: No setting needed. The jump in the file explorer comes from VS Code's own built-in auto-reveal, and the current behaviour is fine. The locate-file setting is out of scope.
- Q: Which separators can the user choose for new documents? → A: Only these four, picked from a list: none (empty), `-`, `.`, `_`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Silence problem reports I don't care about (Priority: P1)

As a requirements engineer whose project deliberately tolerates some Doorstop
findings (for example, skipped levels or missing links from child documents),
I want to switch individual problem reports off in the editor's settings, so
that the Problems panel only shows findings my team actually acts on.

**Why this priority**: Noise in the Problems panel is the most visible daily
annoyance; a panel full of ignored warnings hides the ones that matter. This
setting group also has the most entries and the most user value.

**Independent Test**: Open a repository that produces at least two different
kinds of Doorstop problems. Untick one kind in the settings; confirm all
findings of that kind disappear from the Problems panel while the other kind
stays. Tick it again; confirm the findings come back.

**Acceptance Scenarios**:

1. **Given** the repository has items with "skipped level" and "no text"
   findings, **When** the user unticks the "skipped level" setting, **Then**
   every "skipped level" finding disappears from the Problems panel and every
   "no text" finding remains.
2. **Given** a problem kind is unticked, **When** the user re-ticks it,
   **Then** its findings reappear without the user having to trigger a manual
   re-check.
3. **Given** a fresh install, **When** the user opens the settings, **Then**
   every problem kind is ticked (all reports shown — today's behaviour).
4. **Given** a problem kind is unticked, **When** the user runs "Recheck
   Problems" or edits an item, **Then** findings of that kind still do not
   appear.

---

### User Story 2 - Choose defaults for new documents (Priority: P2)

As a user creating documents from the tree view's "create document" button, I
want to set the default item file format (Markdown or YAML), the UID
separator, and the number of digits once in the settings, so that every new
document follows my project's conventions without me fixing files afterwards.

**Why this priority**: Creating documents is infrequent, but a wrong format or
numbering scheme is tedious to undo once items exist.

**Independent Test**: Set the format to Markdown, separator to `-`, and digits
to 4. Create a document `REQ` from the tree view and add an item to it.
Confirm the item's UID is `REQ-0001` and the item file is Markdown.

**Acceptance Scenarios**:

1. **Given** format = Markdown, separator = `-`, digits = 4, **When** the user
   creates document `REQ` and adds its first item, **Then** the item's UID is
   `REQ-0001` and its file is a Markdown item file.
2. **Given** default settings, **When** the user creates a document, **Then**
   the document uses YAML items, no separator, and 3 digits (Doorstop's own
   defaults — today's behaviour).
3. **Given** the user changes these settings, **When** they look at documents
   created earlier, **Then** those documents are unchanged; the settings only
   apply to documents created afterwards.

---

### User Story 3 - Publish with my own template (Priority: P3)

As a user who publishes documents with a custom Doorstop template, I want to
enter the template name once in the settings, so that every publish from the
extension uses it without me being asked each time.

**Why this priority**: Only users with custom templates benefit; everyone else
keeps the default.

**Independent Test**: Enter a template name that exists in the repository and
publish a document as HTML; confirm the output uses that template. Clear the
setting and publish again; confirm Doorstop's default template is used.

**Acceptance Scenarios**:

1. **Given** the template setting is empty, **When** the user publishes a
   document, **Then** Doorstop's default template is used (today's behaviour).
2. **Given** the template setting names an existing template, **When** the
   user publishes a document, **Then** the output is rendered with that
   template.
3. **Given** the template setting names a template Doorstop cannot find,
   **When** the user publishes, **Then** the publish fails with a message that
   names the missing template and points to the setting, and no partial output
   is reported as success.

---

### Edge Cases

- A problem report the extension cannot classify ("unknown" kind) has its own
  checkbox, so users can also silence findings that match no known kind.
- Unticking a problem kind hides only that kind; a Doorstop error that makes
  validation itself fail (e.g. unreadable repository) is still reported.
- Digits outside a sensible range (below 1 or above 9) are rejected by the
  settings editor and cannot be saved.
- The separator is picked from a fixed list, so an invalid separator cannot
  be entered.
- Settings changed while the server is restarting take effect on the next
  validation run / document creation / publish without reloading the window.
- Workspace-level settings override user-level settings, so a team can commit
  its conventions with the repository.

## Requirements *(mandatory)*

### Functional Requirements

**Problem reports**

- **FR-001**: The extension MUST provide one checkbox setting per problem kind
  that Doorstop validation can report (the check catalogue from spec 014,
  including the "unknown" kind). Default: all on.
- **FR-002**: Each checkbox MUST carry a human-readable label and a one-line
  description of the problem it controls.
- **FR-003**: Findings of an unticked kind MUST NOT appear in the Problems
  panel; findings of ticked kinds MUST be unaffected.
- **FR-004**: Changing any problem-report checkbox MUST update the Problems
  panel without a manual re-check or window reload.

**New documents**

- **FR-005**: The extension MUST provide settings for documents created via
  the tree view: item file format (Markdown or YAML; default YAML), UID
  separator chosen from a fixed list of none (empty), `-`, `.` or `_` (default
  none), and number of digits (default 3).
- **FR-006**: Creating a document via the tree view MUST apply these settings
  to the new document.
- **FR-007**: Changing these settings MUST NOT modify existing documents.
- **FR-008**: The settings editor MUST reject a digits value outside 1–9.

**Publish template**

- **FR-009**: The extension MUST provide a text setting for the template name
  used when publishing documents. Default: empty (Doorstop's default template).
- **FR-010**: When the setting is non-empty, every publish started from the
  extension MUST pass the template to Doorstop.
- **FR-011**: When Doorstop cannot use the configured template, the publish
  MUST fail with an error message naming the template and the setting.

**General**

- **FR-012**: All settings MUST appear under a single "Doorstop" section in
  the editor's settings UI and MUST be settable per user and per workspace.
- **FR-013**: With all settings at their defaults, the extension MUST behave
  exactly as it does today.

### Key Entities

- **Problem-report setting**: one on/off flag per problem kind (identified by
  the stable check id from spec 014).
- **New-document defaults**: item format (Markdown | YAML), separator (none |
  `-` | `.` | `_`), digits (1–9).
- **Publish template**: a template name, possibly empty.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can find and change any of the settings from the editor's
  settings UI in under 30 seconds by searching "Doorstop".
- **SC-002**: After unticking a problem kind, 100% of its findings disappear
  from the Problems panel within 2 seconds, and 0 findings of other kinds are
  removed.
- **SC-003**: 100% of documents created via the tree view after a settings
  change follow the configured format, separator, and digits.
- **SC-004**: An existing user upgrading with no settings changed sees no
  difference in Problems panel contents, document
  creation, or publish output.

## Assumptions

- Locating the open file in the VS Code file explorer is out of scope: that
  jump is VS Code's own built-in auto-reveal, and its current behaviour is
  kept. The Doorstop tree view's auto-reveal stays on its title-bar toggle
  (spec 010).
- Problem kinds are filtered by the extension after Doorstop validation runs;
  where Doorstop itself offers a switch to skip a whole check, the plan may
  use it instead (Constitution II), as long as the per-kind behaviour above
  holds.
- New-document settings apply to the tree view's "create document" action;
  the user is not prompted for these values per document.
- The publish template applies to all publish formats that support templates;
  formats that ignore templates (e.g. plain Markdown) publish unchanged.
- Settings changes take effect without reloading the window.
